# Help Scout MCP Server v2.1.0

## Release Positioning

v2.1.0 adds the first write surface. It is minor, not major, because nothing
about a default install changes: with both write flags unset the server
advertises the same three tools as 2.0, over the same 55 read operations, and
every write path is absent from discovery, schema loading, and dispatch.

Turning writes on adds a fourth advertised tool, `write_help_scout`, and 13
conversation write operations behind it. The Mailbox API has no granular OAuth
scopes, so a token that can read a conversation can also reply to it. That makes
the server the permission boundary, and the gates are configuration an operator
sets deliberately rather than a claim about what the credential restricts.

## Highlights

### A Fourth Advertised Tool

`write_help_scout` executes one write operation using arguments that match the
schema loaded through `describe_help_scout`. It carries `readOnlyHint: false` and
`destructiveHint: true`, which is the worst case for the tool a host is about to
approve, not the best case for a particular call.

Discovery is unchanged: `search_help_scout` labels write results with their
mutation class, `describe_help_scout` reports `mutationClass` and `tier`, and
`read_help_scout` refuses anything that mutates and names the tool that does not.

Write operation names never dispatch directly. No pre-2.0 client ever learned
one, so there is no compatibility debt to honor, and a bare `createNote` call
would slip past the gating, annotations, and confirmation that the write gateway
exists to enforce.

### Two Tiers, Both Off By Default

| Flag | Enables |
| --- | --- |
| `HELPSCOUT_ENABLE_WRITES=true` | Tier 1: the 11 `nonDestructive` and `reversible` operations |
| `HELPSCOUT_ENABLE_CUSTOMER_VISIBLE_WRITES=true` | Tier 2: adds the 2 `externallyVisible` operations |

Tier 2 is additive and inert alone. With both unset, `write_help_scout` is not
returned by `tools/list`, write operations do not appear in search results, and
`describe_help_scout` reports a write operation name as unknown rather than as
gated, so the disabled surface is not a discoverable inventory of what an
operator could turn on.

Advertisement is built once per process, but execution gating is live: every
`externallyVisible` operation rechecks the flags at dispatch, so revoking the
customer-visible gate refuses the next customer-visible write immediately.

### The 13 Operations

Tier 1, `HELPSCOUT_ENABLE_WRITES`:

| Operation | Mutation class | What it does |
| --- | --- | --- |
| `createNote` | `nonDestructive` | Adds an internal note, visible to teammates only |
| `createDraftReply` | `nonDestructive` | Composes a customer reply and saves it unsent |
| `updateConversationStatus` | `reversible` | Sets active, closed, or pending |
| `assignConversation` | `reversible` | Assigns the conversation to a user |
| `unassignConversation` | `reversible` | Returns it to the unassigned queue |
| `addConversationTags` | `reversible` | Adds tags, keeping the existing ones |
| `removeConversationTags` | `reversible` | Removes tags, keeping the rest |
| `updateConversationFields` | `reversible` | Sets custom field values, preserving unlisted fields |
| `snoozeConversation` | `reversible` | Snoozes until a future time |
| `unsnoozeConversation` | `reversible` | Wakes a snoozed conversation |
| `moveConversation` | `reversible` | Moves it to another inbox |

Tier 2, additionally `HELPSCOUT_ENABLE_CUSTOMER_VISIBLE_WRITES`:

| Operation | Mutation class | What it does |
| --- | --- | --- |
| `sendReply` | `externallyVisible` | Emails the customer immediately |
| `publishDraft` | `externallyVisible` | Clears the draft flag, sending the pending reply |

Help Scout replaces the whole list on tag and custom field updates, so those
three operations read the record first and send the merged result. Each write
result carries `operation`, `mutationClass`, `target`, `status`, `result`, and a
`cleanup` block naming how to undo the change. Most of these endpoints answer
with no body, so the result names the read that confirms the new state instead of
claiming confirmation it does not have.

### Draft First

Where an externally visible action has a non-visible variant, the non-visible
variant is the default and the visible one is a separate tier-2 operation.
`createDraftReply` pins `draft: true` and exposes no parameter that flips it into
a send. Composing reply text stays in tier 1 and never notifies anyone. Making a
customer see something takes a deliberate second step under a second flag.

The rule generalizes: no tier-1 operation may accept a parameter that makes it
externally visible.

### Per-Call Confirmation

Enabling tier 2 is a gate, not a bypass. Every `externallyVisible` call must
carry three fields as siblings of `arguments`:

```json
{
  "name": "sendReply",
  "arguments": { "conversationId": "12345", "text": "..." },
  "confirm": true,
  "confirmOperation": "sendReply",
  "targetId": "12345"
}
```

Missing, false, or mismatched values are rejected before any Help Scout request.
The requirement is stated in the `write_help_scout` tool description itself, so a
client reading `tools/list` learns it without a describe call.

These fields never appear in a per-operation schema: the schema describes the
Help Scout request, and confirmation authorizes the call that carries it. A
confirmation or `dryRun` field sent inside `arguments` is refused rather than
ignored, because a caller who misplaces one believes it took effect, and a
misplaced `dryRun` would otherwise perform the live mutation.

### Dry Run

`"dryRun": true` beside `arguments` validates the input and reports the exact
request that would be sent, including the read a read-modify-write operation
performs first. It never contacts Help Scout and never simulates a result, and it
says plainly that Help Scout state was not checked. Help Scout offers no preview
or validate endpoint for these mutations, so that is the honest limit of what a
dry run can claim.

### Retries Exempted For Writes

Reads keep retrying on 429 and 5xx. Every write surfaces the failure instead. A
retried reply is a second customer email and a retried note is a duplicate note,
and a 5xx does not prove the first request failed. Uncertain outcomes clear the
response cache and tell the caller to read the target back before retrying, so a
cached pre-write copy cannot be mistaken for confirmation that nothing landed.

### What Is Deliberately Excluded

- `destructive` operations are not exposed under any flag. No environment
  variable turns them on. Exposing them needs its own contract work, not a third
  flag added by analogy.
- No delete operations of any kind.
- No admin configuration writes: workflows, webhooks, inbox settings, users,
  teams, and tags are read-only.
- No Docs write surface. Docs publishing is externally visible and unscoped.
- No conversation creation. The write dogfood harness seeds its own fixture
  through the raw API rather than adding an operation for a test.

## Verification

- 516 unit and integration tests pass.
- Live dogfood: 185 passed, 0 failed, against the real Help Scout account. Every
  tier-1 operation mutated the `MCP-TEST: write lifecycle fixture` conversation
  over stdio and restored it, verified by reading the conversation or its threads
  back.
- Live stdio screen: 7/7 gateway cells, 9/9 read-only cells, 9/9 tier-1 cells,
  9/9 tier-2 cells.
- Gateway surface assertions confirm exactly four advertised tools when writes
  are on, the write tool's `readOnlyHint: false` and `destructiveHint: true`,
  mutation class and tier on every enabled operation, tier-2 operations reported
  as unknown while their gate is off, and `read_help_scout` refusing a write
  operation with a redirect.
- Upstream denials that cannot be provoked on demand against a real account (401,
  403, 412, 422, 423, 429, 5xx, and network failure) are covered by unit tests.

## Breaking Changes

None. The default advertised surface is byte-identical to 2.0: three tools, 55
read operations, the same server instructions. Existing clients need no change,
and clients that parse `content[].text` keep working.

Enabling writes is opt-in and requires a server restart to change what is
advertised.

## Compatibility

- OAuth2 credentials are unchanged: `HELPSCOUT_APP_ID` and
  `HELPSCOUT_APP_SECRET`.
- Writes run with the private app's user permissions; a credential whose user
  cannot write returns 403 as a structured tool error.
- `HELPSCOUT_DOCS_API_KEY` is still optional and Docs-only.
- The navigator skill (2.0.0) is now standalone: it bundles no server and pins
  no version. One repo URL distributes it everywhere: `/plugin marketplace add`
  in Claude Code, Add marketplace from GitHub in claude.ai and Cowork, or a
  folder copy in any other harness. The MCPB extension covers Claude Desktop
  Chat and Cowork sessions.
- Fixed: the packaged MCPB extension never started its server (the CLI's
  direct-invocation guard did not recognize the extension layout), so installs
  failed with "Unable to connect to extension server". The guard now resolves
  symlinks and accepts the `build/server/cli.js` layout.

## Publish Sequence

Publishing is manual apart from the Docker build.

1. Merge the write-surface branch into `dev`.
2. Open and merge the `dev` to `main` release PR.
3. Tag `v2.1.0` on `main` from the merge commit and push the tag. The tag push
   triggers the Docker build and push.
4. Publish to npm by hand from a pristine worktree of the tag
   (`git worktree add ../release-v2.1.0 v2.1.0`), never from the dev checkout:
   its `dist/` accumulates residue from unmerged branches. Build there, then
   `npm publish --otp=<2FA_CODE>`. There is no CI publish step.
5. Build the desktop bundle with `npm run mcpb:pack` and attach
   `help-scout-mcp-server-2.1.0.mcpb` to the GitHub release.
6. Create the GitHub release from the `v2.1.0` tag with these notes and the
   `.mcpb` attached.
7. Verify public install paths:
   - `npx -y help-scout-mcp-server@2.1.0`
   - navigator skill install from the marketplace
   - `.mcpb` install
   - `drewburchfield/help-scout-mcp-server:2.1.0`
8. Sync `main` back to `dev`.

## Verifying The Install

A connected client with no write flags set should list exactly three tools, the
same as 2.0. With `HELPSCOUT_ENABLE_WRITES=true` it should list four, and
`write_help_scout` should report `readOnlyHint: false`. If a client lists four
tools with the flags unset, it is running a stale process: the advertised surface
is fixed at startup.
